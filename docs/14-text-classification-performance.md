# 14 — 文本二进制判定的等价优化（0.8.2）

> 设计与测量日期：2026-09-17；发行验证完成：2026-09-19。本轮只优化已解码文本中的控制字符计数，不改变文件范围、编码、读取限制、查询、数据库或安全校验。最终交付以09为准。

## 1. 原行为必须保持

旧规则是：任意位置存在NUL即视为二进制；否则统计`ord(c) < 32`且不是TAB/LF/CR/FF的字符，除以**完整已解码字符串长度**，比例严格大于`0.02`才视为二进制。

- 恰好2%不拒绝，略高于2%才拒绝；不把`>`改为`>=`。
- DEL、C1、中文、emoji、组合字符等不能新增为计数范围。
- 先严格解码再判断；BOM优先级、手动编码覆盖、错误状态、256KiB预览截断与5MiB索引上限不变。
- 完整文件读取及前后身份校验仍先执行。预览只检查原有预览范围，不冒充全文件已检查。

## 2. 实现

`files._looks_binary`首先保留全串NUL检查，然后用固定预编译正则`[\x01-\x08\x0b\x0e-\x1f]`枚举真正需要计数的字符。

清洁文本由正则引擎扫描，不再为每个字符进入Python生成器。每遇到一个匹配仍使用原浮点`count / length > 0.02`判断；只有已经足以证明最终结果为二进制时才提前返回。否则遍历全部匹配。它不是抽样、不是只检查文件开头，也不改变阈值语义。

只有文件适配层这一处生产文件改变，无新增依赖、数据库迁移、缓存格式或实验anchor连接。

## 3. 独立验证

- 内部纯函数测试用旧表达式作为独立oracle，覆盖所有0..255码位、四种允许空白、DEL/C1、Unicode、精确边界、多种布局、固定seed样例及5MiB长尾。
- 另一agent只经公开`read_document`和真实`ApplicationService`黑盒检查，不依赖helper：覆盖UTF-8/BOM/UTF-16、编码覆盖、NUL、长尾、预览/完整索引差异、大小上限与取消，核对源文件hash。
- 性能测试不进入单元测试的耗时门槛，不用“运行够快”代替语义一致。

黑盒首轮有一个测试期望错误：UTF-16LE BOM后立即出现NUL会形成`FF FE 00 00`，既有更长BOM优先规则会尝试UTF-32解码。测试已明确保持该默认路径的`needs_encoding`，再手动选UTF-16验证解码后的NUL拒绝；没有为测试改变生产BOM优先级。最终独立黑盒24项通过。
