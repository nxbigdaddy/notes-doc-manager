# 15 — 索引锁竞争恢复（0.8.3）

> 日期：2026-09-21。范围仅为已存在的索引写入可靠性，不改数据模式、事务模式、生产超时或扫描算法。

## 1. 已复现的问题

`Store.set_index_batch`原来把所有SQLite数据库异常都降级为索引不可用。隔离测试在健康缓存上保持写锁后，扫描没有报告可重试错误，而是关闭全文索引能力；解除锁后仍需要用户重建，短暂占用被当作持久损坏。

复现涵盖真实WAL事务开始时的写锁，以及测试用回滚日志模式下提交阶段的读锁。所有锁、模式切换和短超时只作用于测试数据库，生产配置不变。

## 2. 最小修复

- 复用已有`_is_database_busy`识别BUSY/LOCKED及扩展错误码。
- 缓存事务按既有机制回滚，然后抛出`NotesError("database_busy", ...)`；不关闭`fts_available`、不更改原警告、不发布伪造的索引错误状态。
- 旧缓存内容保留，但待更新文档的新代际仍为pending，旧代际不算覆盖。解除占用后显式刷新可正常重试，不要求重建。
- 缺表、损坏数据库等非锁错误仍执行原来的保守降级；没有把所有数据库错误都当作可以忽略的忙状态。
- 不增加循环重试、修改持久化字段或启用实验anchor连接。

## 3. 服务和界面状态

扫描异常现在向订阅者发布`busy=False`与明确“扫描未完成”信息，再保留原错误返回。发布状态本身若失败，不得掩盖原始异常。

读到了正文不等于成功写入索引：缓存已降级不可用时，不再把这些ready读取计入成功索引数量；仍计为未完成，也不会推进整库内容核验成功时间。

## 4. 验证边界

- 真实BEGIN/COMMIT锁、整批回滚、扩展忙错误码、正常重试及真实损坏降级均有Store测试。
- 独立服务测试验证标签/收藏/源文件保留，待处理代际不误命中，订阅者结束忙状态，解除锁后不用重建即可索引新正文。
- 源码/冻结自测加入独立缓存锁探针，锁与连接工厂在finally中恢复，生产超时不变。
- `SearchResult.complete`代表查询执行完成，覆盖不足由`covered/uncovered`说明；本轮没有改变搜索语义。
- 未使用真实用户文件或实际编辑器，不进行大型性能测量。最终全套与发行结果见09。

## 5. 发行验证中的窗口生命周期检查

首次全套1194项通过后，串行源码冒烟流程出现一次`0xc0000005`原生退出。隔离自测报告已生成，GUI报告未生成；匹配的Windows错误事件指向`wxbase32u_vc140_x64.dll`，没有足够信息证明具体根因。随后分别带故障回溯运行self-test、GUI与quick-smoke均成功，不能用这三次成功抹掉先前异常。

静态检查及有界隐藏测试独立确认了一个生命周期遗漏：入口创建的激活轮询定时器在窗口调用Destroy后仍处于运行状态。测试立即停止它再处理销毁事件，没有故意触发原生崩溃。

当前将500ms激活轮询交给MainFrame持有，关闭/销毁时停止，迟到回调先检查关闭状态。该改动针对可复现的定时器遗漏；不声称已经证明或彻底解决上述原生异常的所有可能原因。原始证据保留于`.artifacts/native-smoke-failure-0.8.3-20260921.json`，修改后必须重新完成回归与冻结验证。
