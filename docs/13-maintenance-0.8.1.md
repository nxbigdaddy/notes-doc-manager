# 13 — 0.8.1 有界维护

> 日期：2026-09-17。不增加新业务功能：收敛在线恢复确认、发行依赖证据和实际扫描路径性能分析。交付结果见09。

## 1. 普通在线JSON恢复的确认绑定

隔离复现证明0.8及以前的普通恢复存在检查/确认间隙：

- 检查A后，同一路径换成计数相同的B，原流程会恢复未经确认的B。
- 检查后新增的标签，原流程会被恢复覆盖。保护快照存在、正文不变，但这不等于恢复了用户所确认的版本。
- 原启动恢复`RecoveryManager`已有双指纹，不受同一种缺口影响。

0.8.1协议：

1. `inspect_backup`返回统计及`signature`、`current_signature`。
2. 候选指纹绑定实际读取的JSON字节SHA256、规范路径、文件身份、大小及时间；解析和统计使用同一次读取的字节，不另读一次猜测一致。
3. 当前状态指纹包含文档库/规则、ID/关联、标签/收藏/最近打开/编码覆盖、机器用户设置和智能列表；排除索引、文件大小/修改时间、库在线状态及内部备份/维护记账，避免派生刷新使确认失效。
4. 应用服务只接受`confirmed=True`加两个有效64位十六进制指纹；缺失不能恢复。底层Store的同步单步API仍可由受控测试/工具直接调用，不是GUI绕过确认入口。
5. 保护快照前核对候选和当前状态；保护快照后，在Store门锁和SQLite写事务内再次核对当前语义及候选文件，才修改元数据。
6. `backup_changed`或`metadata_changed`拒绝且不自动重试，用户必须重新检查/确认。保护复制后才发现变化时，已生成保护快照保留。
7. 读取期间大小/身份/时间不稳定、链接/重解析路径或超过100MiB拒绝。第二次候选复核使用有界流式hash，不再分配另一份完整JSON。

这是单应用门锁、SQLite事务和文件复验组成的保守保护；不承诺抵御同权限敌手在最后检查后的任意系统级替换。已经解析并匹配指纹的候选内容不从随后改变的文件重新取值。

### Windows运行时差异

本机真实导出采用临时文件重命名发布；最初测试发现重命名后的`stat`与`fstat`的`st_ctime_ns`不同，导致未变文件被误拒绝。当前以可用`st_birthtime_ns`（无该字段的平台回退ctime）联合dev/inode/size/mtime比较，同时独立校验全文hash。真实重命名导出回归已纳入，不靠忽略文件内容变化来规避差异。

## 2. 已提交与后续失败分开

- SQL替换事务失败仍回滚。
- 元数据已提交但缓存重建失败，返回`restored_index_pending`；服务仍清理旧重试/监听状态并安排补扫。
- 已提交后的状态刷新等失败返回`restored_followup_failed`。
- 两者都明确“管理信息已恢复，不要重复恢复”，GUI刷新当前状态和列表，不把已提交事实说成完全未发生。

GUI使用独立检查代际：再次选择或取消选择使旧检查失效，关闭后不提交；确认对话框运行的事件循环中若意图改变，旧确认也无效。统计文案不显示两个hash。普通筛选/文件夹缓存只在确实提交后清理，活动智能列表ID仍遵守0.8的不自动退回全库规则。

## 3. 发行依赖证据

维护脚本只读取已有项目私有runtime、venv及发行目录，不执行被检查二进制、不下载或更新依赖、不改旧发行包。

- 原生`.exe/.dll/.pyd`逐文件哈希，能与本地来源字节一致时记录证据；仅同名不能证明来源。
- 原文许可、包元数据声明和未覆盖项分开，只有固定版本/原文hash匹配审批清单的本地notice才复制。
- 清单输出机器JSON、人类可读说明及原文副本；缺失/无法证明的原生组件关系明确列pending。
- **技术清单不是法律审计、完整SBOM、商业分发批准或签名验收。** 未覆盖项不能因为写出NOTICE就标记完成。
- 首次只允许在新构建目录生成；已验证发行目录不改写许可产物，重验采用只读校验。

## 4. 有界性能分析

过去的Store基准不等同于完整服务扫描。新增诊断仅针对隔离生成样本，正常服务`scan`命令进入写线程，再对实际扫描函数收集cProfile与分阶段统计。

- 本轮最多一次1000文件/20MiB基线；不启用实验`index_session`，不扫描真实库，不自动跑500MiB。
- 临时目录唯一且限定在本项目`.artifacts`，清理前复核解析路径；不重试已被策略拒绝的旧临时目录清理。
- 记录全部源文件、脚本/锁和实际runtime指纹，前后变化则不能作为稳定基线；原始profile和JSON留在外层。
- 函数累计时间有包含关系，不能把嵌套阶段相加冒充总耗时。分析结论只适用于该样本，不外推大库达标或GUI交互成绩。
- 只根据实测瓶颈再决定最小低风险优化，不为获得漂亮数字降低数据验证或盲目重复跑大型样本。

- **报告严格保留`status=incomparable`、`measurement_valid=false`，不是合格性能基线。** 原因是脚本在采集runtime-before后才探测host，触发`socket.py`/`_socket.pyd`懒加载；已有runtime文件hash未变，但两次加载集合不一致。未修改原报告为通过，也没有再次跑1000样本。

- 下一步候选是分析SQLite批量写入语句/提交成本及正文控制字符逐字符计数；暂不修改生产扫描策略、不采样跳过校验、不启用锚连接。任何优化仍须单独语义回归和受控测量。
