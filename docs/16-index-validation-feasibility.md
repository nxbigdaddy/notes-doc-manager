# 16 — 索引前元数据批量读取可行性（2026-09-21）

## 结论

**不修改生产实现，不为此发布新版本。** 批量读取可以减少SQLite调用，但目前测得的绝对收益很小，不足以证明值得增加兼容处理及维护成本。0.8.3源程序和发行包保持不变。

本轮只评估`set_index_batch`在写缓存前的逐文档元数据校验；未修改索引事务、同步级别、连接生命周期、缓存格式、批次大小或实验anchor。

## 1. 独立候选与语义验证

实验脚本`benchmark_index_validation.py`比较：

- 原逻辑：每项`SELECT * FROM documents WHERE id=?`，按原输入顺序核对代际、大小、时间、截断等。
- 非生产候选：按实际变量限额分块读取必要四列，再按原顺序验证全部输入。

兼容边界包括混合代际/状态、缺失ID、全批次预验证、输入顺序、实际SQL变量限额及非字符串ID。SQLite文本亲和性可能接受某些非字符串参数，不能直接用Python字典查找假装完全等价；候选为此保留回退路径。

31项隔离测试通过，未修改`src`。这证明已覆盖的候选语义，不代表已适合投入生产。

主agent合并转发探针测试后，针对性共33项通过，Ruff通过；记录`.artifacts/index-feasibility-tests-20260921.xml`。随后只读核对0.8.3的全部生产源文件、EXE与ZIP哈希，均与已发布清单一致；没有启动用户程序或重新打包。

报告：`.artifacts/index-validation-20260921T072325-6b15b03ffe17.json`。

同一已准备的内存连接、1000行、每批50项、交替5轮：

|---|---:|---:|
| SELECT次数 | 1000 | 20 |
| 校验中位数 | 5.5374 ms | 1.7562 ms |

绝对节约约3.78ms/1000行。这不是磁盘库吞吐、整库索引或p95结果；不能将历史剖析中包含FTS写入的execute总时间均摊给这些SELECT。

## 3. 原生产代码的SQL调用成本观察

另做一次1000文件/20MiB真实服务扫描，保留原SQL、原连接创建逻辑、事务和正文校验，仅通过转发代理计时execute/executemany/close；没有启用cProfile、GUI、监听、编辑器或anchor。定时代理仍有开销，故也不是无仪器的吞吐基准。

报告：`.artifacts/index-call-cost-20260921T072422-975abcd89c40.json`。

- 完整扫描/索引覆盖1000项，源代码、runtime和正文前后指纹不变，结果有效；全程约35.449秒。
- 2000次逐ID元数据SELECT合计execute时间约0.01117秒；该SQL形状同时出现在代际失效与批次校验中，**不能说全部属于批次校验**。
- 1000次旧缓存row_id查询合计约0.16288秒。
- 缓存正文插入约5.936秒，缓存事务约14.707秒，缓存连接关闭约2.257秒；元数据事务约4.812秒、关闭约3.266秒。
- execute计时不含随后的fetchone/fetchall和Python校验；不同工具的时长不能直接相减计算全应用提速。这里只能支持“没有证据表明逐ID校验读取是主要瓶颈”的判断。

首版报告键名`metadata_row_validation`过窄。原JSON和原脚本快照`.artifacts/index-call-cost-probe-20260921-first.py`已保留，未改写数据；工具后续格式2改名为`metadata_document_lookup`并明确按SQL形状分组。本轮没有再次跑1000样本。

## 4. 下一步边界

已知耗时主要落在缓存写入/事务与关闭路径，但这不授权降低数据持久性、取消回滚保障、任意加大批次或直接启用尚未解释的实验锚连接。

如继续性能工作，必须先给出内存、取消响应、短操作等待和恢复语义的受控验证方案，再决定是否值得一次更大样本。既有500MiB/Windows 11等未验收项仍未完成，不把本轮无发布变更说成这些目标已达标，也不为凑版本持续修改已验证代码。
