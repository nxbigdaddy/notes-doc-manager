# 04 — 数据模型与搜索

## 1. 数据责任

| 数据 | 权威来源 | 是否可完全重建 |
|---|---|---|
| 文档正文、磁盘路径、文件时间 | 文件系统 | 不可依靠管理器数据库恢复原文件 |
| 标签、收藏、文档 ID、路径关联、个人设置 | metadata.db | 不可；需备份 |
| 文件大小、索引状态等派生字段 | 文件系统 / 扫描结果 | 可重新计算 |
| 正文缓存、检索倒排数据 | search-v2.db（0.3.0） | 可从在线且可读的文件重建 |

两个数据库不做跨库原子事务依赖。通过文档 ID 和代际核验搜索结果；任何索引故障不得牵连管理信息。

> v0.3 实现提示：以下表格为目标模型。当前实现的精确 DDL 在 `infrastructure/store.py`，例如键名称采用 snake_case、时间/迁移信息尚未全部扩展。通过测试确认的行为与差异记录于 [09](09-iteration-log.md)，不能把目标字段表当作已经完整落地的 schema。

Python 方案通过标准库 `sqlite3` 访问两个数据库，表结构和数据责任保持不变。连接与线程边界见第 7 节；切换语言并不免除 SQLite 原生能力和冻结发布包验证。

## 2. 元数据模型

时间统一存 UTC Unix 毫秒，界面转换为本地时间。文档 ID 使用应用生成的 UUID，路径不是主键。

| 表 | 主要字段 | 约束与说明 |
|---|---|---|
| Libraries | id、name、root_path、root_path_key、enabled、availability、rules_json、created_at | root_path_key 唯一；停用保留记录 |
| Documents | id、library_id、relative_path、path_key、file_name、extension、size_bytes、modified_at、availability、in_scope、content_generation、index_status、encoding_override、is_favorite、last_open_requested_at、created_at、updated_at | library_id 外键；`(library_id, path_key)` 唯一 |
| Tags | id、name、name_key、created_at | name_key 唯一 |
| DocumentTags | document_id、tag_id | 联合主键；显式标签删除只级联关联 |
| Settings | key、value_json | schema 化校验，不接受任意执行命令 |
| SchemaMigrations | version、applied_at | 记录成功迁移版本 |

0.4.0另增加可重建派生表 `document_file_identities(document_id, identity)`，外键删除级联。它不增加Document固定列，不进入JSON导出/恢复和管理信息变更指纹；metadata schema版本仍为1，使旧版固定列INSERT仍兼容。完整数据库快照可能包含该派生表，但从JSON或旧版运行回来后需要重新采集身份，不能相信跨机器身份。

0.8.0的智能列表是不可重建的管理信息，不使用派生表兼容策略。首次成功保存前做保护快照，在单个事务中创建`smart_lists(id,name,name_key,query_json)`并升metadata schema2；未使用功能的旧库仍为1。列表保存版本化白名单JSON，不保存SQL或分页。ID引用保留，删除标签不级联删筛选，运行时明确拒绝失效范围。schema2导出format2备份，旧版拒绝而非忽略。详见12。

建议索引：

- Documents：文档库 / 管理范围 / 状态、修改时间、收藏、最近打开。
- DocumentTags：按 tag_id 查文档。
- Tags：名称规范化键。

首版采用有版本号的建表 SQL 和迁移，不在设计阶段将字段表当作可直接生产运行的 DDL。

标签名展示值去除首尾空白并做 NFC 规范化，name_key 采用 `unicodedata.normalize("NFC", display_name.casefold())`；初值长度上限为 50 个 Unicode scalar，空值和同键重名一律拒绝。大小写折叠不是简单改小写，必须测试字符扩展及重名行为 [S15]。

### 2.1 状态拆分

- 文档库 availability：`online / offline / inaccessible / unknown`。
- 文档 availability：`present / missing / unreadable / unknown`。
- 文档 in_scope：扩展名和排除规则是否仍允许管理。
- index_status：`pending / ready / skipped_large / skipped_binary / needs_encoding / error`。

库离线不批量将文档改为 missing；移出规则不删除标签；停用库不删除文件或元数据。

## 3. 文件身份与路径规则

1. 根目录保存规范绝对路径，文档保存相对路径。
2. 在应用层使用 Windows 路径规则及序数不区分大小写比较；保留原始大小写用于展示。路径不做正文/标签的 NFC 归一化，避免把不同磁盘名称合并。
3. 不依赖 SQLite 内置 NOCASE 或 Python `casefold()` 实现完整 Windows 路径比较；路径键与归属判断由 WindowsPathAdapter 统一实现，并用非 ASCII、大小写及硬链接样例验证。文本搜索的归一化算法不能用于文件身份；键冲突未核实前拒绝合并。
4. 首版拒绝已知启用大小写敏感模式的目录；无法可靠校验的目录不承诺支持。
5. 根目录不得重叠；路径归属检查必须含目录分隔符边界，不能用简单字符串前缀。
6. 默认跳过符号链接、junction 等重解析点，不递归跨出根目录；硬链接按路径视为不同文档。
7. 文件路径相同的普通保存或原子替换视为同一逻辑文档，保留 ID 和标签。
8. 完整可靠的同库 rename 事件可保留 ID，但须验证旧记录、新路径、目标冲突及受影响子树。
9. 事件缺失、跨库移动、离线移动、复制与删除组合，不自动猜测同一文件。旧记录标记缺失，新路径另行登记。
10. 不以“同名”或“内容哈希相同”自动合并，避免把复制件的标签错误迁移。

0.4.0已实现上述第8条的窄范围：正常运行期间的完整新鲜**直接单文件**移动事件，加上既有身份基线、旧路径真实缺失和目标身份双次实测。目录、链式/冲突事件、跨库、关闭期间、硬链接和未知身份不自动推断。身份只是组合证据，不是永久不复用的全球标识。

P1 手动重新定位只接受同库内、符合规则、未绑定其他文档的新路径。若目标已经登记，先提示冲突；首版不提供自动记录合并。

## 4. 搜索库结构

0.3.0 使用独立 `search-v2.db`（缓存schema版本2），旧 `search.db` 不打开、不改写、不删除。首次升级以源文件重建新索引，暂时保留两份缓存的磁盘占用；这与同一新缓存内部不重复保存正文是两个概念。

- `indexed_documents`：row_id（INTEGER 主键）、document_id（唯一）、generation、body、encoding。正文完整归一化后只保存在该表一份；其余派生源信息仍由元数据/后续模型管理。
- `document_fts`：FTS5 external-content 虚表，`content='indexed_documents'`、`content_rowid='row_id'`、trigram tokenizer，保留默认 `detail=full`。

v0.1/v0.2 暂选普通存储型FTS以简化实现；0.3.0通过真实SQLite回归后改用external-content [S5]。新增/删除/更新触发器在同一缓存事务中维护FTS；删除和替换使用旧body对应的删除指令，不把普通FTS的双写方式带入新缓存。旧可执行文件继续使用旧缓存，避免触发器与手动维护冲突。

首次新建或迁移缓存时，先把元数据代际递增并标记pending，再事务性创建缓存schema；包括原本pending的记录，防止旧版本缓存以相同代际复活。未知未来缓存版本只降级为文件名搜索，重建操作也不覆盖它。

**隐私提醒：新旧搜索缓存均包含可读的正文副本，不能当作不敏感的缓存。**

启用前记录 `sqlite3.sqlite_version` 和编译选项，并在临时数据库实际创建 FTS5 trigram 表、插入中文及执行长短词查询。Python 自带 sqlite3 不等于所选构建必然启用 FTS5 [S4/S5]；开发环境与冻结发布包都必须探测。失败时保留文件名搜索，明确提示正文搜索不可用；M1 重新选择依赖组合，不在线下载未知扩展或静默声称满足全文需求。

## 5. 查询语义

### 5.1 规范化

- 用户输入去除首尾空白；空输入视为普通列表。
- 正文解码后统一 CRLF/CR 为 LF，保留原始文件不变。
- 查询和检索文本统一执行 `NFC → str.casefold() → NFC`，不受用户区域设置影响；文件名搜索也使用此文本算法，不改变实际文件路径 [S15]。
- 不做简繁转换、拼音匹配或词义扩展。
- 长度按 Unicode scalar 计算，不按 UTF-16 code unit 计数。
- 首版最大查询长度暂定 256 个 Unicode scalar。

记录文本规范化算法版本与 `unicodedata.unidata_version`。升级 Python 或更改算法时重建搜索索引；标签键如需重算，先报告冲突再迁移，不能直接覆盖。v0.1 尚未产生真实数据库，本次只是将旧语言的伪 API 设计改成 Python 规则，不声称已经完成数据迁移。

用于检索的字符串与原始预览分离。高亮需要维护或重新计算规范化映射，不能把规范化后的偏移直接当原文件列号。

### 5.2 查询执行

1. 先按启用库、在线状态、范围、文件夹、标签和收藏筛选元数据。
2. 文件名采用归一化后的字面子串比较。
3. 归一化后的正文查询达到 3 个 Unicode scalar 时，使用转义后的 FTS5 字面短语生成候选，再验证完整子串。
4. 归一化后为 1～2 个 Unicode scalar 时，对已索引正文执行参数化字面子串回退查询，例如 `instr`，不交给 trigram MATCH。原始查询长度仍用于输入限制，不能混淆两个长度。
5. 不把用户输入当作 FTS 运算符。`"`、`*`、`%`、`_`、括号和 SQL 片段必须按字面值处理；SQL 参数化和 FTS 查询语法转义是两层不同工作。
6. 特殊输入无法可靠通过 FTS 候选时允许回退字面扫描，并显示较慢状态。
7. 合并文件名与正文命中、去重、校验元数据代际，再排序分页。

FTS5 trigram 的短查询限制来自官方资料 [S5]；上述回退、筛选和字面语义是本项目的设计选择。

首版无需 BM25 相关性调优。普通查询排序为“文件名命中优先，组内修改时间倒序，文档 ID 排序”；最近打开视图按打开时间倒序、文档ID稳定排序，在当前元数据筛选范围内取最近100条，再应用关键词和分页。

0.3.0将范围过滤、代际关联、候选校验、排序和分页移入同一个SQL读取快照，只为当前页创建Python DTO及摘要。取消仍必须返回complete=False，数据库忙不能被误报为缓存损坏。

### 5.3 跨库一致性

- 文件变更后 metadata.content_generation 增加，旧正文缓存不可再作为有效命中。
- 搜索结果仅接受 generation 与 metadata 当前值一致的索引记录。
- 查询开始时捕获筛选快照，结果展示前再次核验状态与代际；结果页是查询快照，不承诺分页期间实时不变。
- 删除或停用后的孤立索引记录异步清理；在清理前也必须被元数据过滤。
- 后台 reconciliation 检查 pending、缺失索引与代际不匹配，修复跨库写入中断。
- 搜索覆盖计数按同一过滤范围计算，不能用全库 ready 数冒充当前筛选覆盖数。

### 5.4 短词、大结果与超时

- 短词回退可能扫描大量正文，不保证与长查询同速。
- 默认每页 100 条；后台分批执行、可取消，初始超时 10 秒。
- 超时和取消返回 `complete=false`；界面不得把部分结果数标成最终总数。
- 不暗中截取前 N 个文件并显示“无结果”；性能不足时提示缩小范围。
- 测量未达标时可评估独立 bigram 索引，不在首版默认引入新搜索服务。
- SQL 绑定使用 sqlite3 参数占位符，候选 ID 分批传入，避免超过所选 SQLite 的变量上限；不靠字符串插值规避限制。
- SQL 执行前安装 `Connection.set_progress_handler` 检查请求的取消标记和期限 [S4]；逐行读取/Python 过滤阶段也检查。取消导致的中断与真实数据库损坏分开上报，任务结束清除回调。

## 6. 索引更新

稳定读取 → 解码 → 规范化 → 检查任务代际 → search-v2.db 中正文/FTS触发器事务更新 → metadata 标记 ready。

- 读取前后检查大小、修改时间及已收到的事件代际；变化则重排队。
- 检查无法证明任意外部写入下的绝对原子快照，保证通过重试和补偿校验最终一致。
- 文件改成超限或无法解码时，旧代际正文立即失效，不继续搜出旧内容。
- 默认单文件正文索引上限为 5 MiB 源字节，超限只参加文件名搜索，不索引开头冒充全文。
- 修改编码 override 会增加代际并重建该文件索引。
- 缺失、排除和停用记录的正文默认不参与搜索；可清理缓存而保留管理信息。
- 不把索引正文用于恢复源文件。

## 7. 数据库策略

- 用 `sqlite3`，不引入 ORM 或连接池。写连接在唯一写线程内创建、使用、关闭；读连接由读任务线程独立拥有，保持 `check_same_thread=True`，不跨线程传递 cursor。
- 统一连接工厂显式指定事务策略，暂选 `autocommit=True`，启动后配置 PRAGMA，再用 SQL `BEGIN IMMEDIATE` / `COMMIT` / `ROLLBACK` 管理写事务；不依赖默认的 legacy 行为，也不把此模式下的 Python `commit()` 当显式 SQL COMMIT 使用 [S4]。
- 每个连接启用外键检查、busy timeout 初值 5 秒；数据库初始化时启用 WAL。PRAGMA 在无活动事务时设置并读取确认。
- metadata.db 的同步级别采用 FULL；search-v2.db 采用 NORMAL，丢失缓存可重建。
- 短事务、串行写入，不在事务中等待文件读取或编辑器启动。
- JSON 导出等一致性读取显式 `BEGIN` 并及时结束，避免长时间持有读快照导致 WAL 膨胀；备份和扫描调度相互协调。
- 使用参数化 SQL；迁移按受控语句和事务边界执行，不依赖 `executescript()` 与外层事务在所有模式下隐式保持一致。
- `with connection` 不等于关闭连接，任务及恢复流程必须显式 `close()`。备份和恢复不假定存在可自动清理的框架连接池。
- 当前版本的索引重建在写队列内先失效代际，再事务清空/重建自己的缓存；损坏缓存保留诊断副本。旧search.db及未知未来schema均不擅自覆盖，不影响元数据。
- schema 迁移必须可测试、可失败回退；不兼容备份不得强行导入。

## 8. 备份数据格式

逻辑导出 JSON 至少包含：format_version、app_version、exported_at_utc、libraries、documents、tags、document_tags、可迁移设置。

- 保留 UUID、相对路径、原库路径、收藏和编码 override。
- 不导出正文缓存、临时队列、错误堆栈和机器专属运行状态。
- 导入校验重复 ID、路径越界、外键缺失、格式版本与文件大小上限；备份输入初值限制为 100 MiB，超限先拒绝并说明，不无界载入内存。
- 首版恢复是**替换管理信息**，不做复杂合并；显示预览并要求明确确认。
- 根目录在新机器不存在时保留离线，不猜测或自动迁移文件。
- 运行时编辑器路径等不从备份自动激活；设置须重新确认。
- 恢复完成后所有正文索引重新验证或重建。

当前JSON格式仍为 `format_version=1`：保留文档库规则、文档身份/路径、标签、收藏、编码；`settings` 导出为空，恢复不激活导入的机器设置。0.2.0已增加自动备份内部状态与轮换登记，不能从外部JSON伪造本机快照所有权。

自动备份内部记账和每库内容核验时间都使用保留键前缀，排除在管理信息变更指纹之外；SQL迁移仍须独立版本管理，应用小版本号不等于DDL自动兼容保证。
